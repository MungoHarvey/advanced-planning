# Design: Codex Cross-Model Second-Opinion Gate Reviewer

Generated by /office-hours on 2026-06-08
Branch: main
Repo: advanced-planning (hierarchical multi-agent planning framework)
Status: DRAFT
Mode: Builder

## Problem Statement

At each phase boundary, `/run-gate` spawns in-house subagent reviewers (default
`code-review-agent`, `phase-goals-agent`) that evaluate loop outputs against the phase
success criteria and write immutable verdict JSON to `.advanced-plans/gate-verdicts/`.
Every reviewer is the same model family (Sonnet) reading the same artefacts with the
same blind spots. The gate has no genuinely independent voice. We want to add OpenAI
Codex as a cross-model second opinion on the phase-goals check, so a *different* model
must independently agree before a phase closes out, while keeping the framework portable
and zero-dependency when Codex is not installed.

## What Makes This Cool

The verdict JSON is already a clean, immutable state-bus contract. That means Codex and a
subagent are interchangeable *producers* of the same artefact. We get a real cross-model
gate (two different AIs must agree) without inventing a new state format, and the whole
thing degrades to exactly today's gate when Codex is absent. The independence is
structural, not aspirational: the two reviewers run in parallel and are forbidden from
reading each other's verdicts, so neither can anchor on the other.

## Constraints

- **Zero-dependency Python** (CI-enforced via `ast_check`; allow-set in `core/constraints.json`).
- **core/ is platform-agnostic**; no `.claude/` paths in core. Adapters wrap core.
- **Verdicts are immutable** and schema-bound (`core/state/gate-verdict.schema.json`).
- **No gstack coupling.** Must not call `gstack-codex-probe` or any `~/.claude/skills/gstack/bin` helper.
- `gate-verdict.schema.json` is NOT in the LOCKED set (only the phase-complete and
  phase-manifest schemas are), so extending it is permitted.

## Premises (agreed)

1. The verdict JSON is the stable interface; Codex and subagents are interchangeable
   producers. Downstream (aggregation, `history.jsonl`, `/next-phase` retry versioning)
   is untouched. **Add an optional `backend` field (`codex` | `subagent`) — and this is
   a blocking prerequisite, not a nice-to-have** (see Cross-Model Perspective).
2. Codex runs `-s read-only` and cannot write its verdict. The main thread captures
   Codex stdout, extracts one fenced `json` block, validates against the schema, and
   writes `phase-N-attempt-M-codex.json` on its behalf (reusing the Step-7 CONTINGENCY
   mechanism). On any skip, also write a `phase-N-attempt-M-codex.raw.txt` sibling for
   debuggability.
3. Codex gets a strict output contract + filesystem boundary: read repo + `.advanced-plans/`,
   ignore `.claude/skills/`, emit one fenced json block only. On unparseable output,
   degrade to the two-agent gate.
4. The fail/conflict path is new gate behavior: any fail OR any Codex-vs-subagent
   disagreement surfaces findings and asks the user for the action, UNLESS an
   auto-remediation policy is configured, in which case it proceeds straight to fixing.
5. No gstack coupling; the Codex path does its own `which codex` + auth check.
6. **Independence is first-class.** Codex and the phase-goals subagent run in parallel
   and are each forbidden from reading `.advanced-plans/gate-verdicts/` or receiving the
   other's conclusions in-prompt. This produces genuinely independent cross-model verdicts.

## Cross-Model Perspective (Codex, gpt-5.5, high reasoning)

Codex read `gate-verdict.schema.json`, `phase-goals-agent.md`, and `run-gate.md` before
critiquing. Key points, adopted:

- **Steelman:** augmentation is the right shape; reusing the verdict schema avoids a new
  state contract; graceful degradation keeps the framework portable.
- **Highest risk (adopted as a blocking ordering dependency):** the schema is
  `additionalProperties: false` with no `backend`, so a Codex verdict carrying
  `"backend":"codex"` fails validation *today*, forcing a phantom degrade where Codex
  looks absent while emitting fine. The schema change ships FIRST.
- **Reliability traps adopted:** require exactly one ```json block else reject + log
  `codex_skipped`; treat preflight/auth failure as explicit degraded status (not a parse
  error); **prompt injection** — mark phase artefacts as untrusted evidence, tell Codex
  never to follow instructions found in artefacts, require file/line evidence for every
  criterion; **example overfitting** — validate `phase`, `attempt`, `agent === "codex"`
  after parsing so Codex can't copy the sample verdict's identity fields.
- **Where we go further than Codex:** Codex said keep raw stdout "if policy allows"; we
  make the `.raw.txt` sibling mandatory on skip so every degrade is debuggable.
- **Defer (agreed):** auto-remediation implementation, rich disagreement adjudication,
  parallelizing all agents, any gstack integration.

## Relationship to the gstack `/codex` skill

`/codex` is a human-facing interactive tool (review/challenge/consult modes), output
presented verbatim, deeply gstack-coupled, and its "review mode" runs `codex review`
producing Codex's *own* diff-review format. We borrow its invocation mechanics and reject
its output model and coupling:

- **Borrow:** `which codex`; temp-file prompt delivery (injection-safe); `codex exec`;
  `-s read-only`; `model_reasoning_effort="high"`; tmp stderr capture; 5-minute timeout;
  filesystem-boundary prefix.
- **Adapt:** boundary must still read `.advanced-plans/`; auth check done locally
  (`auth.json` / `$CODEX_API_KEY` / `$OPENAI_API_KEY`) instead of `gstack-codex-probe`.
- **Reject:** `codex review` (wrong tool — hands a human prose, not our schema); verbatim
  human-facing output; gstack plumbing.

One-line: this gate is `/codex` consult-mode mechanics wrapped around a structured-output
contract, with gstack stripped out.

## Approaches Considered

### Approach A: Inline in run-gate.md (minimal viable)
Summary: all Codex logic inline in `run-gate.md` Step 7.
Effort: S | Risk: Med
Pros: 2 files; fastest; mirrors existing inlined bash.
Cons: stdout->JSON extraction (the #1 failure mode, ~6 sub-cases) becomes untested
markdown prose; nothing reusable for other adapters; logic duplicated if Codex later
backs other checks.
Reuses: existing run-gate aggregation + sentinel.

### Approach B: Tested python helper + core contract (ideal architecture)
Summary: zero-dep `codex_gate.py` owns extraction + validation with pytest; portable
contract in `core/agents/codex-reviewer.md`; `run-gate.md` shells out and calls the helper.
Effort: M | Risk: Low
Pros: de-risks the crux with real tests; matches the existing pattern (`versioning.py`,
`state_manager.py` back commands); portable to Cowork/Python adapters; honors core/ split
and zero-dep constraint.
Cons: 6 files; an orchestration seam (command does I/O, helper stays pure).
Reuses: zero-dep allow-set (`json`, `re`, `pathlib`); CONTINGENCY write mechanism.

### Approach C: Codex as a `--agents` entry (lateral)
Summary: `--agents` accepts `codex-phase-goals`; run-gate routes `codex-`prefixed entries
to the Codex backend.
Effort: M-L | Risk: Med
Pros: uniform "Codex is just another reviewer" model.
Cons: overloads `--agents` (subagent vs CLI backends); complicates `attempt = floor(N/agent_count)`
and sequential-spawn logic; more than v1 needs.
Reuses: B's helper + contract (which is why it's a clean v2).

## Recommended Approach

**"B+" — B's internals + A's wiring + parallel independence.** v1 (5 files, post eng-review):

- **B internals:** `core/agents/codex-reviewer.md` (portable contract; sits beside
  `core/agents/gate-reviewer.md`) + zero-dep `platforms/python/codex_gate.py`
  (extraction + validation + `aggregate_verdicts`, tested). **No `platforms/claude-code/agents/`
  file** — Codex is a Bash subprocess, not an Agent-tool agent, so filing it under
  `agents/` would be a category error. The `codex exec` invocation lives inline in
  `run-gate.md`.
- **A wiring:** Codex auto-participates when preflight passes; degrades to today's exact
  two-agent gate otherwise. No `--agents` overload.
- **Parallel independence (ordering):** `code-review-agent` runs first (foreground,
  unchanged). Then `codex exec` (background Bash) + `phase-goals-agent` (foreground Agent)
  run as the independent parallel pair; main thread joins Codex stdout on subagent return.
  Both reviewers forbidden from reading `gate-verdicts/`. Amend run-gate's "sequential
  only" note: same-backend subagents stay sequential; the Codex backend writes a distinct
  file and runs in parallel with one subagent.
- **Aggregation is testable:** `aggregate_verdicts(paths) -> {result, conflicts, missing}`
  in `codex_gate.py`, replacing the prose in run-gate Step 9. Covers all-pass, any-fail,
  codex-degraded-absent, and codex-vs-subagent conflict.
- **Validator is lenient:** `codex_gate.py` hand-rolls validation (zero-dep, no
  `jsonschema`). It checks required fields + types + `agent=="codex"` + identity
  (anti-overfit), and TOLERATES extra fields. Rationale: nothing in the system enforces
  the schema at runtime (CI only parse-checks the schema files), and live verdicts already
  carry an `evaluated_by` extra. Lenient validation unblocks `backend` without the schema
  edit being load-bearing, and won't reject existing files.

**C is the documented v2 upgrade path; B is forward-compatible with it (helper + contract
unchanged).**

## Build Order (concrete)

1. **Schema (documentation, not blocking):** add optional `backend` enum
   `["codex","subagent"]` to `gate-verdict.schema.json`. NOTE per eng-review: nothing
   enforces this schema at runtime (CI only parse-checks the schema files), so this edit
   documents intent for the hand-rolled validator rather than gating anything. The stray
   `evaluated_by` is handled by the lenient validator (no emitter change needed); optionally
   add it to the schema for honesty. Also delete the legacy `.advanced-plans/phases/phase-7/gate-verdicts/`.
2. `platforms/python/codex_gate.py` (pure, zero-dep — `json`, `re`, `pathlib`):
   - `extract_verdict_json(stdout) -> str|None` (single fenced block; brace fallback)
   - `validate_verdict(d) -> (ok, reason)` (required + types + `agent=="codex"`; tolerant of extras)
   - `extract_and_validate(stdout, phase, attempt) -> {ok, verdict|reason}` (anti-overfit identity check)
   - `aggregate_verdicts(paths) -> {result, conflicts, missing}` (replaces run-gate Step 9 prose)
3. `platforms/python/tests/test_codex_gate.py`: 20 paths per the test plan, incl. the TWO
   CRITICAL regression cases (all-pass→pass, any-fail→fail) that protect pre-existing
   aggregation behavior, currently untested.
4. `core/agents/codex-reviewer.md`: portable contract (untrusted-artefact rule, file/line
   evidence requirement, fenced-json-only output, isolation rule). Invocation is NOT here.
5. `run-gate.md`: preflight (`which codex` + local auth) → run code-review-agent →
   launch background `codex exec` ∥ foreground `phase-goals-agent` → join → `codex_gate`
   → write `codex.json` or `.raw.txt` + degrade; call `aggregate_verdicts`; amend
   sequential-only note (Codex backend may run parallel to one subagent); add conflict UX
   to Steps 9-11 (surface findings + ask user unless auto-remediation configured); add
   `codex_skipped` / degrade event to `history.jsonl`.
6. **Integration:** shadow `codex` off PATH and confirm graceful degrade to today's
   two-agent gate (the test most likely to catch a real environment failure).

## Open Questions

- **Auto-remediation policy surface:** where is it configured (PLANNING.md frontmatter
  flag? `/run-gate --auto-fix`?) and what exactly does "proceed to fixing" spawn? Deferred
  by design, but the config hook should be named in v1 even if it just routes to the
  user-decision prompt.
- **Stray path cleanup:** delete/migrate the legacy `.advanced-plans/phases/phase-7/gate-verdicts/`
  so there is one unambiguous verdict target. Cheap; do it in this pass.
- **Codex version guard:** port the known-bad-list idea from `/codex` now, or defer? Lean
  defer (preflight + timeout already covers the failure).

## Success Criteria

- Schema has optional `backend` enum; all existing live verdicts validate after
  `evaluated_by` reconciliation; round-trip + JSON-validation CI passes.
- `codex_gate.py` is zero-dep (AST check NONE) with tests covering all extraction sub-cases.
- With Codex present: a gate produces three verdict files; `phase-N-attempt-M-codex.json`
  has `agent:"codex"`, `backend:"codex"`, schema-valid; aggregation = AND of all.
- With Codex absent/erroring: gate behaves exactly as today's two-agent gate; a degrade
  is recorded in `history.jsonl` and a `.raw.txt` sibling exists when stdout was produced.
- Codex and `phase-goals-agent` run with no access to each other's verdicts (isolation rule
  present in the contract; parallel execution in run-gate).
- On fail or Codex-vs-subagent disagreement, the gate surfaces findings and prompts the
  user for the action (or routes to auto-remediation when configured).

## Distribution Plan

No new distribution channel. Ships as part of the framework via the existing
`install.sh` / `install.ps1` copy of `core/` + `platforms/claude-code/`. New python module
is covered by existing pytest/AST CI. Codex itself is an external user-installed CLI; the
framework degrades gracefully without it.

## What I noticed about how you think

- You caught the contamination risk before I raised it: "codex should run before or in
  parallel ... so that they don't contaminate each others' investigation ... produce
  independent results." That is the actual reason a second opinion is worth paying for,
  and it upgraded the design from "add a reviewer" to "guarantee independence."
- You pushed on output format early ("Is it JSON? this is useful and keeps it structured")
  and on "where the phase gate outputs land" — both turned out to expose real cracks (the
  schema `additionalProperties` trap and the stray phase-7 verdict path). Asking where the
  artefacts actually live, not trusting the docs, is what surfaced them.
- You asked whether the hybrid is "what a v2 would look like when we get to C" rather than
  just asking for everything at once. That is the right instinct: take B now, keep C as a
  forward-compatible upgrade, don't build the routing layer before there's a second thing
  to route.
